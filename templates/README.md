# .render/ — this project's renderer configuration

Everything project-specific for the
[render](https://github.com/durchnull/render) plugin lives in
this directory: the project's **pages**, each designed here, all rendered
by the plugin's engine. The engine itself stays inside the plugin
installation and is **imported, never copied**.

## What lives here

| File | Role |
|---|---|
| `config.py` | project-wide: `ROOT`, optional `OUT_DIR`, `LANG`, `EXTRA_CSS`, `STRINGS`, `INDEX`, `INDEX_FILENAME` defaults |
| `pages/<id>/` | one folder per page: `__init__.py` (title, description, hero, section list) + one module per section — renders to `output/<id>.html` |
| `kinds/<name>.py` | optional: your own data-driven page kind, when none of the plugin's fits |
| `content.py` | project-specific gather/format helpers on top of the generic core |
| `render.py` | thin entry point: `python3 .render/render.py [--all\|--check\|…]` |
| `engine_locator.py` | resolves the installed engine; run directly, it prints the path |
| your own page scripts | standalone renderers built on `page_api` (see below) |
| `output/` | generated: one HTML file per page, `index.html`, the `.cache/` fragment store, `--preview` pages — regenerable, safe to gitignore |

## Keeping it current

Two of the files above are the **plugin's**, not the project's:
`render.py` and `engine_locator.py` hold no project-specific settings, and
this README and `pages/__init__.py` describe a contract the plugin defines.
A copy that stays behind is how a project ends up unable to find the engine
at all, so **run `/render:init` again** after updating the plugin — it
replaces those four, fills in any that are missing, and never touches
`config.py`, `content.py` or anything under `pages/<id>/`. Version control
is what makes the replacement reversible.

Everything else is yours and stays exactly as you wrote it.

The engine is the reason this is such a small job: it is imported from the
installation rather than copied here, so it is current the moment the plugin
is. Nobody has to track which version wrote these four either — the engine
compares them against the installation on every run and says one line when
they differ.

## Start here: `output/index.html`

The engine keeps one page nobody declares — a card per rendered page, with
its title, its description and a link to it, rewritten on every run. Open
that one and navigate from there. Each card says what its page says about
itself: `TITLE` and `DESCRIPTION` for a page you designed, the kind's own
summary for one instance of a family. Turn it off with `INDEX = False` in
`config.py`, rename it with `INDEX_FILENAME`.

## Adding a page

A page is a folder: `pages/<id>/__init__.py` declares `TITLE`,
`DESCRIPTION` and `SECTIONS`, sibling modules build the sections — the
contract lives in `pages/__init__.py`. The engine discovers, renders,
caches, checks and indexes every page; nothing is registered anywhere else.
The plugin's `new` skill walks through it.

When the pages differ only in their data, declare `KIND` + `SOURCES`
instead of `SECTIONS` and the engine renders **one output per matching
file** — the glob is the lifecycle, so archiving an instance means moving
its data file out of the glob and running `--prune`. The plugin ships the
`questionnaire` kind; `/render:questionnaire` walks through it.

## Off-limits

- **Never copy or edit the engine.** The plugin installation is read-only;
  `engine_locator.py` finds it, `page_api` is the only stable interface to
  it. A copied engine forks silently and never receives another update.
- **No custom hex colors or CSS that bypasses the design system.** Colors,
  typography, spacing and components come exclusively from the engine's
  tokens — `check_page()` / `render.py --check` enforce this.
- **Output stays self-contained** — no CDN, no external resources.

## Standalone page scripts

When a page cannot be a declared page — it must land outside this
directory, or be generated by tooling the engine doesn't run — write a
script here that imports `page_shell`, `check_page` and the components
from `page_api`, and verifies itself with `check_page()` before writing.
The `new` skill carries the pattern and a runnable skeleton.
